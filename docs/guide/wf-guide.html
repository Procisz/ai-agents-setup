      1Overview

      wf turns Claude Code into a small team of AI assistants. You say what you want in plain words, the team does the work, and you get a short report of what was done.

      How it works

      1. You askOpen wf in your project and describe what you want, the way you would ask a colleague.
      2. It checks that it understood youIf something is unclear, it asks short questions, each with answers you can simply pick, and every time it shows what is already decided, what is still open and which decision it needs from you now. It keeps asking back until nothing is open. Then it shows a short summary of what it is going to do, in plain words, and shows it again after every change until you approve or cancel. Until then it changes nothing.
      3. You approve onceNothing starts until you approve that summary. After that it works on its own and does not interrupt you, unless something makes the approved summary impossible to follow.
      4. The team does the workOne assistant plans the steps, others make the changes and test them, and specialists step in when they are needed.
      5. You get a short reportWhat was done, what was checked, and anything that still needs your attention. Its temporary notes are cleaned up.

      Who is on the team

      The orchestrator

      The project manager: talks with you, hands out the work, keeps track of it and writes the report. Beyond a quick answer or a one-line fix, it does not do the work itself.

      The planner

      Works out the steps before anyone starts, for every task, small or large.

      The coder

      Makes the changes. Several can work side by side on separate parts.

      The tester

      Checks that everything still works.

      The docs writer

      Updates the project's written documentation.

      The reviewer

      A second pair of eyes, when you ask for one.

      The debugger

      The troubleshooter, called in when the same problem comes back.

      The git assistant

      Saves and shares the finished work, only when you asked for it.

      Why it works this way

      Quick and economical

      Easy jobs go to small, fast AI models; hard or risky jobs go to the strongest ones. How hard a job is counts, not how many files it touches.

      Few interruptions

      One approval, then it works alone. The choices it made on its own are listed in the report.

      Safe by default

      It never publishes your work unless you asked, never straight onto the main version (it opens a proposal that can be reviewed first), and it backs up your settings before it installs anything.

      2Install

      Node 22 or newer

      Check with node --version. On macOS: brew install node.

      Claude Code 2.1.312+

      From the native installer, on macOS and Linux curl -fsSL https://claude.ai/install.sh | bash (Windows: see 11). Check with claude --version; older: claude update.

      git and gh

      The repository is private: the GitHub CLI signs you in and clones it. In your projects the git agent needs git, and a pull request needs gh signed in.

      1. Sign in to GitHub
        gh auth login
        Answer GitHub.com, HTTPS, yes, web browser. Then Logged in as your account.
      2. Clone, in any folder where you keep projects
        gh repo clone Procisz/ai-agents-setup
        cd ai-agents-setup
        This is your clone folder. It can be anywhere; every later node wf.mjs step runs here.
      3. Check that you are in the clone folder
        ls wf.mjs
        Expected: wf.mjs. "No such file" means another folder: cd to your clone first.
      4. Install
        node wf.mjs install
        A header box, your config and launcher folders, ✔ Claude Code 2.1.312 and ✔ Lint: 0 errors, 0 warnings, then five steps: tiers, agents, models, skills and a summary. For everything with the recommended skills, press enter on every list and once more on Install (twelve presses the first time: tiers, agents, models, a skills list for each of the eight roles, then Install). It ends with ✔ Applied 103 changes. Backup: <stamp> (103 on a fresh macOS or Linux install with everything ticked, 107 on Windows), ✔ verify: claude plugin validate passed, ✔ verify: 103 files match. and Next: run wf in a project folder. A node from nvm or another version manager adds a ⚠ The hooks will run ... warning (see 11).
      5. Only if install printed a PATH hint

        It looks like ... is not on PATH. Add it: echo '...' >> ~/.zshrc, then open a new terminal. Run the echo ... >> ~/.zshrc command from it (from echo up to the file name), open a new terminal, then:

        command -v wf
        A path ending in .local/bin/wf.
      6. Health check, from the clone folder
        node wf.mjs doctor
        Last line wf doctor: all good., or all good (1 warning). with the warn line above it.

      The five install steps

      Each step starts with Step n of 5, an icon and a title, then two to four lines on what you decide: what the step controls, what unticking does and what the default is. Every list starts from your saved answer of the last install, or the first time from the defaults: every tier, agent and model ticked, and each role's recommended skills. After enter the list makes way for one result line, such as ✔ Tiers: T1, T2, T3, T4 (T5 runs as T4).

      1. 📊 Tiers

        Which task sizes get their own agents: T1 small, T2 medium, T3 large, T4 major, T5 critical (how a task gets its tier: 6). T0, questions and tiny edits, needs no agents and is always there. Default: all five. Keep at least one: a task of a missing tier runs as the nearest installed tier, the higher one on a tie.

      2. 🤖 Agents

        Which workers are installed: planner, docs, coder, tester, reviewer, debugger and git. Each role has one agent per installed tier, except git: one wf:git for every tier. Only the roles your tiers use are listed; the orchestrator is the main thread and always installed. Default: all of them. The coder is locked, needed by every tier; the work of a missing agent moves to a coder (see below). Without the debugger, a repeated failure gets one more coder round, then the report. Without the git agent, the work stays uncommitted and the report lists the git commands.

      3. 🧠 Models

        Which models wf may use: Opus 5.5, Sonnet 5.5 and Haiku 5.5, strongest first, each with how many installed agents are set to it. Default: all three. Keep at least one: an agent whose model is unticked, the orchestrator too, runs on the nearest ticked model, the stronger one on a tie, with the same effort.

      4. 🧩 Skills

        One list per installed role, the orchestrator first: the ticked skills are built into that agent's prompt. Default: each role's recommended skills; required ones are locked. An unticked skill stays in the library, where agents read it when a task needs it.

      5. 📋 Summary

        A table of every agent with its tier, model and effort (* marks a stand-in model), one line per missing tier or agent and per unticked model that an installed agent was set to, with what happens instead, the skill counts and the file plan, with the v1 migration block if there is one. Then one last question.

A list taller than the terminal shows the part around the cursor, with ↑ n more above and ↓ n more below lines, and scrolls as you move; a narrow terminal gets a shorter key line.

      Install now?
      InstallWrite the files now; a backup comes first
      Change choicesStart again at step 1 with these answers ticked

      Install is the only confirmation: no Apply N changes? question follows. Only enter chooses: space does nothing here but show press enter to choose. Cancel, or esc, ends with Cancelled: nothing was written.

      The box, the icons and the colors appear only in a terminal: cyan for the cursor and titles, green for ticks, yellow for warnings, dim for hints and locked items. NO_COLOR turns the colors off. FORCE_COLOR forces the colors, also in a pipe, but never the box, the icons or the wrapping. In a Windows console outside Windows Terminal the icons fall back to ASCII ([x], [ ], >, +, !). With TERM=dumb they fall back to ASCII too, and the lists become numbered questions: type the numbers to toggle, then press enter to accept. Without a terminal the output is plain text with no box, icons or wrapping, and no colors unless FORCE_COLOR is set.

      Saved answers, --yes and --reset

      The install manifest saves all four answers: tiers, agents, models and skills. The next install starts every list from them, and anything added to wf since comes with its default: the git agent, for example, comes ticked on the first install that knows it, while a git agent you unticked once stays unticked. diff, doctor (its choices line) and every reinstall use them too, so a smaller setup survives updates.

      node wf.mjs install --yes
      Asks nothing, like a run without a terminal: installs the saved answers, or everything with the recommended skills the first time.
      node wf.mjs install --reset
      Starts from the defaults instead of the saved answers: in a terminal every list starts as the first time, and together with --yes it installs everything with the recommended skills. --skills-reset is its old name and still works.

      What a missing tier, agent or model means

      The orchestrator's instructions get one note per tier or agent you left out and one per unticked model that an installed agent was set to (Everything is installed. when there is none), and it follows them in every task.

      Not installedWhat happens instead
      a tierA task of that size runs as the nearest installed tier, the higher one on a tie: a missing T3 runs as T4, or as T2 when T4 is missing too (T1 to T5). The summary's Tier line says so, and the final report repeats it on its Setup line.
      plannerA coder of the task's tier writes plan.md in a separate plan-only round before the implementation, at every tier.
      docs agentEach coder does the docs steps of plan.md in its own package (wf: docs: in the coders' packages), following the docs-writing skill.
      testerEach coder writes and runs the tests of its package after its code (wf: tests: in the coders' packages), following the testing skill: expected values come from the approved summary and plan, never from the code's own output.
      reviewerWhen you ask for a review, a coder of the task's tier does a separate read-only review round with the checks and severity scale of the code-review skill; the summary's Review line and the report's Setup line say so.
      debuggerA failure that comes back for the same reason gets one more coder fix round, within the cap of 2 per phase; when it fails again, it goes to the report (see 4).
      gitThe git phase leaves the work uncommitted, also when you asked for git work: the summary's Git line says so and keeps every git action you asked for (a commit, or a push and pull request, a branch name or base, a merge, or any other action such as deleting branches), and the report lists the commands for exactly that to run yourself (git switch -c <branch>, git add -- <the task's files>, git commit -m "<subject>", and for a push or pull request git push -u origin <branch> and gh pr create --fill, with --base <base> when you named a base, for a merge gh pr merge --merge, and for any other action the git or gh command that does it, for example git branch -d <branch> or git push origin --delete <branch>).
      a modelIts agents run on the nearest ticked model, the stronger one on a tie, with the same effort. The install summary marks them with *.

      Updating

      From the clone folder:

      git pull
      node wf.mjs install
      In a terminal the five steps come back with your saved answers: enter on each list and Install keeps them. Nothing new: 0 changes: wf is up to date. An update that brings a new role (the debugger and the git agent came this way) shows it ticked in the agents step; until you install again, doctor's choices line warns, for example debugger is new: node wf.mjs install adds it, or debugger, git are new: node wf.mjs install adds them on an install older than both (after no saved choices; on an install from before the installer choices). A new agent of a role you already have, such as wf:planner-t1, is added without a question.
      Coming from v1Install finds the v1 manifest and migrates once, after backing everything up: it removes the v1 agents and hooks, replaces the launcher and house rules, puts back your own agents/Explore.md when it still matches, and removes only the v1 entries from settings.json (your own hooks and settings stay). The home folder trust and ai-agents-setup/cost/ are left alone. restore --to <stamp> brings v1 back. Close any running v1 wf session first: it loses its v1 agents and hooks.

      3First run

      Open a terminal in one of your projects (a git repository is best: without one there is no git phase) and start wf:

      wf
      Claude Code opens with the wf orchestrator as the main thread, in the Concise output style. Type or paste your request. On Windows, type wf.cmd in PowerShell and cmd: plain wf opens the firewall console there (see 11).
      Try a question first

      "What do the test scripts of this project run?" A question is tier T0: a direct answer, no approval, no agents. It changes nothing; when it suggests changes, it asks which ones to prepare as a task (at most 2 suggestions, then None for now and Something else), and those go through a summary and your approval.

      Then a change

      "Add a --json option to the stats command." A new option is usually tier T2. While a point is open it asks back, with answers you can pick; then you get a short summary and the approval question, then status lines and a report.

      You can also pass the request at once; any other arguments go to claude unchanged:

      wf "what do the test scripts of this project run?"
      TipsStart with T0:, T1:, T2:, T3:, T4: or T5: to force a tier; a tier you did not install runs as the nearest installed one. Say "commit" for a commit on a feature branch, or "push" or "open a pull request" for branch, push and pull request; otherwise nothing is committed. Add "merge it" only when you want the merge too. You can ask for any other git action in plain words, such as "delete the merged branches" or "commit on main". Without the git agent installed nothing is committed even when you ask: the report lists the git commands to run yourself. Ask for a review to get the reviewer (or a coder's read-only review round when the reviewer is not installed). "approved, no questions" in the request approves in advance.

      4The flow

      You Opus Sonnet Haiku Checks and cleanup Dashed: only when needed
      1. 1
        orchestratorTriage
        Silent. Scores difficulty and risk to pick the tier (6), picks the phases and the git wish. A T0 question gets its answer here. One obvious edit skips the rest of the flow: the approval question with a one-line summary, then the orchestrator makes the edit itself (5).
      2. 2
        orchestratorDiscussion
        Until you explicitly approve: every turn ends with choosable options, never about HOW; nothing changes before Approve.
      3. 3
        youSummary and the one approval
        After Approve: no more questions until the report, except one for a hard contradiction that makes the summary impossible to follow.
      4. 4
        git agentBranch setup
        Only when the approved summary wants the work itself done on a new branch, or names a base branch other than the current one.
      5. 5
        plannerPlan
        At every tier: Haiku at T1, Sonnet at T2 to T4, Opus at T5. Packages are sized by what a worker must understand, not by file count: a mechanical edit across many files stays one package. The plan may raise the tier, never lower it.
      6. 6
        docs agentDocs
        When the project has docs the change affects, or you asked. Before the code.
      7. 7
        codersImplementation
        One coder per plan package, up to 5 at once for packages that depend on no other open package and share no file. Each runs the fast checks.
      8. 8
        testerTests
        When the project has tests, or you asked. Always after the code.
      9. 9
        tester or coder, reviewerVerification
        The project's own checks (lint, typecheck, build) run once, in the last worker round: the tester's, else a coder's checks-only round. The reviewer only when you asked. Failing checks and blocker or major findings go back to a coder, at most 2 fix rounds, and each fix round runs all the checks again; a failure that comes back for the same reason goes to the debugger (below).
      10. 10
        git agentGit
        Only when the approved summary asks: any git work its Git line names, such as a commit on a branch, branch, push and pull request, a merge, or another git action.
      11. 11
        orchestratorReport and cleanup
        Stops everything that still runs, deletes the task folder, then prints the short report.
      With workers, the orchestrator only delegatesBeyond T0, planning, docs, code, tests, checks, reviews and git are all worker rounds; the orchestrator writes nothing but its own task notes in .work/ and runs read-only git. During triage and the discussion it reads only what it needs to understand your request (file names, a quick look); the planner explores the code after the approval. Up to 5 coders at once is wf's own limit (Claude Code allows more): they share one working tree, their checks run side by side, and every result lands in the orchestrator's context.

      Coders, testers and the docs agent run on Haiku or Sonnet depending on the tier (6). Workers decide open choices themselves and list them as assumptions in the report. This is the flow with everything installed: when you left an agent out at install, its work moves to a coder of the tier, and without the git agent nothing is committed (see 2).

      Fix rounds and the debugger

      A failure is a failing check or test, or a blocker or major review finding, after a coder's work. The orchestrator records each one in progress.md with a signature: the check or test name and the core of its error (without paths, line numbers or timings), or a finding's file and claim. A worker whose check fails gives one line per failing test with its first error line and saves the full output to a log in notes/, so the orchestrator can tell the same failure from a new one. Each failure is open, fixed or reported. A failure in code the task did not touch is pre-existing and goes straight to the report, and minor review findings are only reported: neither gets a fix round.

      1. 1
        coderA new failure: a coder fix round
        As before: the coder fixes it and reruns the failing checks. At most 2 coder rounds per phase.
      2. 2
        debuggerThe same failure again: the debugger
        Instead of another coder round. It runs alone: running coders finish first, and no other worker that edits files starts until it is done. It gets the signature, what each attempt tried and the files involved. It reproduces the failure, finds the root cause with evidence, applies the smallest fix, reruns the failing check and the related checks, and reports the root cause.
      3. 3
        orchestratorThe last run decides
        The orchestrator decides by the last run of the exact failing command alone: the debugger's own rerun, or a coder's checks-only round when the debugger ran none (for a review finding, a recheck). Passes: the task goes on (noted as possibly flaky when the debugger could not reproduce it). Still failing: no further round, also in a later phase; the report lists it under Not done or failed with the debugger's root cause.

      The debugger runs at most once per signature and twice per task, and its runs do not count against the 2 coder rounds. A different failure after its fix is new: a normal coder round within the cap. It never hands off: when its context fills up, it ends with its analysis so far. It runs on Sonnet 5.5 low at T1, Sonnet 5.5 medium at T2, Sonnet 5.5 high at T3, Opus 5.5 medium at T4 and Opus 5.5 high at T5 (6). Not installed, already run for that failure, or already used twice in the task: a repeated failure gets one more coder round within the cap, then the report.

wf: implementation: 2 coders started (P1, P2)
wf: verification: lint pass, typecheck pass, build fail
wf: verification: fix round 1 started (build: Cannot find module x)

wf: verification: debugger fixed build: Cannot find module x

      Session names

      At your first message a hook (hooks/title.mjs) asks a small Haiku model for a short name made from that prompt and sets the session title to the name in sentence case with spaces and no prefix, for example Fix login timeout: the tier is not known yet. If the model does not answer within 12 seconds, the name is built from the first words of the prompt. An empty prompt or one that starts with / names nothing.

      After the session's first approval, at your next typed message, the session is renamed once to wf(T<n>)- plus that task's short name in the same style, for example wf(T3)-Login fix. The tier <n> comes from the Tier line of the approved summary; without a readable Tier line the new name has no prefix. Later approvals in the same session never rename it, and a tier raise by the planner does not either. Older [WF] and wf- names keep working.

      After /clear the old title is gone and no title is shown; nothing is named until your next typed message, which names the new session.

      A title you set yourself is never overwritten. The hook sends one small Haiku request per session. A live install gets the hook after you run the installer again.

      Nothing left behind

      During a task wf works in <project>/.work/<YYYYMMDD-HHMM-slug>/ (summary.md, plan.md, progress.md, handoff notes, notes/), and .work/.gitignore holds *, so git never sees it. At the report the keep-warm watcher and every worker stop, and wf-clean deletes the task folder, and .work/ too when nothing else is in it. Only the context ledger stays, one small file per session with each agent's token count, in state/ of the install folder, pruned after 7 days.

      When a session ends mid-task, the next wf session in that project asks at your first message: Resume (no new approval), Discard (deletes the task folder; project files stay), Leave it or Something else (type your own answer; an unclear one gets the question again). A task folder that another live wf session is working on (active in the last 75 minutes) is left alone: it gets no question, and wf-clean refuses to delete it. A new request you type while a resumed task runs waits for that task's report.

      5The approval

      While points are still open, every turn of the discussion ends with a question with answers you can pick: at most about 3 questions per turn, each with 2 or 3 answers, the recommended one first and marked (Recommended), and always a last answer, Something else, where you type your own (every question wf asks has it). It never asks about git, the tier, the phases, docs, tests or a review: the summary states them, and you change them there with Change something. The first question starts with a short picture of where things stand:

      📍 Where we are
      • ✅ Decided: a --json option for the stats command; the plain text output stays
      • ❓ Open: should --json also cover the summary line?
      • 👉 Now I need: your answer on the summary line

      A point never drops out of that picture: it moves from Open to Decided, also when you leave it out. As soon as nothing is open, the orchestrator prints a short summary in plain words, for example:

      🎯 What you want
      • The stats command gets a --json option that prints the same numbers as JSON
      🔒 What stays the same
      • Everything else, including the plain text output
      🚀 What will run
      • 📋 Plan and implementation
      • 📝 Docs: the README lists every option
      • 🧪 Tests: the project has tests
      • 🔎 Checks: lint and typecheck
      🌿 Git: leave uncommitted: nothing is committed 📊 Tier: T2: new user-facing behavior in one module, needs new tests ⏰ Estimate: about 15 to 30 minutes 👉 Now I need: your answer below: approve all of this, change something, or cancel.

      The Tier line gives the tier with the short reason from triage. The Estimate line is the wall-clock time from your approval to the report, judged from the tier, the phases and the size of the task (typically T1 5 to 15 minutes, T2 15 to 30, T3 30 to 60, T4 60 to 120, T5 120 minutes or more, given in hours above 2 hours); every summary has it. The Git line follows what you asked. The usual forms:

      You askedGit lineWhat the git agent does

      a commitcommit on a branchcommits the task's own files on a feature branch
      a push or a pull requestbranch, push and open a pull requestcommits on a feature branch, pushes that branch and opens a pull request
      another git action, e.g. delete merged branchesdelete the merged branches, local and remoteruns exactly that action

      Any git action you ask for goes on the Git line in plain words, alone or after one of these forms, for example commit on main and push it, or branch, push and open a pull request, then merge it and delete the branch. The Git line names every git action you asked for, with the branches, tags and remotes you named, and nothing you did not ask for: the git agent does exactly what it says. Unless you ask otherwise, a commit lands on a feature branch and a push comes with a pull request. , then merge it is added only when you asked for the merge, the branch name or base when you gave one, and ; branch set up before the work when you want the work itself done on that branch from the start, or when you named a base branch other than the current one, so the new branch starts from that base while the working tree is still clean. Without the git agent installed, a git wish becomes leave uncommitted: no git agent is installed; asked: <the Git line it would have, with the branch, base and merge>; the report lists the commands, so the report lists the right commands even after a compaction or a resume.

      Approve this summary? After that I work without questions until the report.
      ApproveStart the work; no more questions until the report
      Change somethingSay what to change
      CancelDrop this request; nothing changes

      A summary too long for one question is split at a section break over two questions asked together, Approval 1/2 and Approval 2/2, each with Approve, Change something, Cancel and Something else. It is approved only when you pick Approve in both; Cancel in either cancels, and any other pair counts as Change something.

      Before Approve

      The orchestrator only reads and talks: not a single line changes in any file or setting. Every turn shows where things stand and ends with choosable options (only a turn in which the orchestrator compacts itself ends with one short line, and the picture comes back right after); it asks back until nothing is open, then shows the full summary with Approve, Change something, Cancel and Something else on every turn until you pick Approve or Cancel. Only Approve, a typed answer that only approves, or "approved, no questions" in the request starts the work; "ok" or "do it" said earlier, or an approval with a question or change in it, does not. After any change the summary is shown again in full. The summary names every change, also outside the project, and what it does not list is not approved. Points you dropped in the discussion are listed under Left out. The picture and the summary sit inside the question, so they are always on screen.

      After Approve

      No questions until the report. Two exceptions: a hard contradiction that makes the summary impossible to follow (one question: the recommended way out, one alternative, stop the task or Something else), and the resume question when a later session finds the task unfinished (see 4).

      You can still talk

      Write at any time: the orchestrator answers briefly, follows a change that drops or narrows the work, says in one line that anything new waits for the report, which lists it under Follow-ups as Waiting: <it> (your next message about it starts its own summary and approval), and stops everything when you ask it to.

      T0 tiny edits

      One obvious edit: an approval question with the same four answers (Approve, Change something, Cancel, Something else), its text a one-line summary (naming the file when it is outside the project, saying nothing is committed and the time it takes, usually about 1 minute) followed by Approve this edit? After that I make it and reply in one or two lines. After Approve the orchestrator makes the edit itself, runs the project's fast check for that file when there is one, and replies in one or two lines: no task folder, no agents. Asking for a commit, push or pull request makes it T1 so the git agent can do it; without the git agent it stays T0 and the reply lists the git commands.

      8Context and cache

      100 percent always means the full 1M token window, so the zones are absolute.

      nothing
      buffer: decide
      hand off, compact
      0 500K 800K 850K backstop 1M
      Measured after every tool call

      A hook reads each agent's own transcript and adds a wf context: notice: entering the buffer, every further 50K, and from 800K every 5 tool calls.

      Workers hand off

      In the buffer a worker estimates what it still needs. When used plus needed would pass 800K, it finishes the current step, writes handoff-<role>-<n>.md and ends with Status: handoff; from 800K it does that at once, after only the edit in hand. The orchestrator starts a fresh worker of the same agent from the note, and before it resumes a finished worker for a fix round it checks that worker's tokens with wf-agents. The reviewer writes no file: the orchestrator saves the note from the end of its Open issues. The debugger writes no note: it ends blocked instead, with its analysis so far, and a rerun of the failure decides.

      The orchestrator compacts itself

      In the buffer it estimates what the rest of the task needs. When that stays under 800K, nothing happens. Otherwise it starts no new worker and, once none runs, calls mcp__wf__compact and ends its turn. Past 800K it does that at once, whatever runs.

      1. The wf plugin's module hooks/compact.mjs runs the compaction when the orchestrator's turn ends, because a plugin can make Claude Code compact only between turns.
      2. In the buffer it waits until a turn ends with no subagent running, so no worker result arrives during the compaction. From 800K it compacts at the turn end whatever runs, even without the call.
      3. A PreCompact hook lists what the summary must keep, and when the orchestrator called the tool the module adds its next step. Right after an approval the orchestrator first writes the task folder, summary.md and progress.md, because only summary.md carries an approval through a compaction.
      4. After a compaction the orchestrator asked for, with no worker running, a message that starts with wf compaction done wakes it. It comes from the plugin, not from you, and approves nothing. The orchestrator rereads progress.md, summary.md and plan.md and goes on. Otherwise the next worker result or your next message wakes it.
      5. The orchestrator never calls the tool in the turn that ends with the report or a T0 answer, and a turn that ends with the report drops a queued compaction, so nothing follows the report (past 800K that turn is still compacted, without a wake-up). A /clear, a resume or a turn that ends below 500K drops a queued compaction too. The tool refuses a call below 500K or from a worker, and a turn the wake-up started never wakes the orchestrator a second time.
      Interactive sessions onlyPlugin compaction needs an interactive session, which is how wf runs. In a headless claude -p run the module registers no tool and only the engine's compaction at 850K applies. Each compaction the module runs shows a dim transcript line such as wf: compacting the orchestrator's context at 812K, a queued one that waits shows wf: compaction waits until no worker runs (2 running) once, and a failure shows wf: compaction failed: ..., never in state/hook-errors.log. The engine's 850K compaction also stays as the backstop inside a long turn.
      Why wf never sets autoCompactWindowautoCompactWindow and CLAUDE_CODE_AUTO_COMPACT_WINDOW redefine the window itself, so 100 percent would become the smaller number. The launcher sets only CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=86.74, which moves the trigger: 86.74 percent of 980,000 (1M minus the 20K output reserve) is 850,052 tokens. Lint refuses the other two; keep them out of your own settings.json too.

      The prompt cache

      Each agent has its own cache, set in its frontmatter as experimental.cacheTtl: coder and debugger 1 hour, tester, planner, docs, reviewer and git 5 minutes. The orchestrator keeps the main-thread default, 1 hour on a subscription. The launcher no longer sets CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL, because that variable beat the per-agent setting. A cache entry lives 60 minutes (1 hour agents) or 5 minutes (5 minute agents) from the agent's last request.

      0 minlast request 58 minkeep-warm ping 60 min: expiry
      • Right after the approval the orchestrator starts the wf-keepwarm watcher in the background. It finds the main thread and every subagent of the session by itself, from the session's ledger, finished ones included, so the orchestrator passes no agent list (--agents still works for an agent the ledger does not hold). It polls every 20 seconds and costs no tokens while it waits.
      • When the main thread or a 1 hour agent (coder or debugger) has been idle 58 minutes, or a 5 minute agent (tester, planner, docs, reviewer or git) has been idle 4 minutes, the watcher exits with one ping line per agent that is due and wakes the orchestrator. That turn refreshes the main thread; a worker gets wf keep-warm ping: reply ok only. A worker that is still running is not pinged, and the git agent's reply ok is ignored: its result stays final.
      • A 5 minute agent is pinged only while its last real work is at most 30 minutes old (a ping is not work). After that the watcher ignores it, and resuming it pays the cache rewrite.
      • After 6 main-thread pings in a row with nothing else happening (about 6 idle hours) it stops; your next message starts it again. At the report it is stopped.
      • The 5 minute setting is read from the Claude Code binary, not from its documentation, and is not checked live yet.

      9Safety

      The git guard

      A hook checks every Bash command that mentions git or gh (on Windows every such PowerShell command too) and every Monitor command, in wf sessions only. It sees through bash -c (its positional parameters too), env, sudo, xargs, find -exec, operators and subshells.

      WhoRead-only git and ghEvery other git and gh command: add, commit, push, gh pr create, merge, reset, force ...
      Workersallowedrefused
      The orchestratorallowedrefused
      wf:gitallowedallowed: the guard does not check it; the approved Git line sets what it does
      • Read-only means status, diff, log, show, blame, grep, ls-files and the other read forms, fetch [origin [<branch>]], and gh read forms. A read that points git at another program through a config override or an environment variable (a pager, an editor, an ssh command) is refused too, for example GIT_PAGER=delta git log, also when an earlier export in the same command set the variable.
      • When the guard cannot even start or times out (10 seconds), the command is blocked. Other hook errors go to state/hook-errors.log and never block; only the compaction module's failures show as a dim line in the transcript instead (8).
      • The guard cannot see git writes hidden inside script files or package scripts, nor variables a sourced file sets; the house rules forbid routing a git write through them. An allow-git file from an older wf version gives nothing: the guard no longer reads it.
      wf guard: subagent wf:coder-t1 may not run "git commit -m test": only wf:git runs git and gh writes; leave the changes in the working tree for the orchestrator.

      The orchestrator's refusal ends with delegate them to wf:git only when it is installed and the approved summary asks for git work, else leave the work uncommitted and list the commands in the report.

      The git agent

      wf:git (Haiku 5.5, medium effort, one agent for every tier) is the only wf agent that writes git. The orchestrator starts it only when the approved summary asks for git work: a branch before the work when the summary says so, and the git phase at the end. It has no tools list, so it also gets MCP servers you add later, such as a GitHub one.

      Only what you asked

      It does only the git work the Git line names, and nothing it does not name. It has no branch, force or history limit. Without a named branch it commits on a feature branch, and the change reaches main, master, develop or the default branch through a pull request.

      Only the task's files

      The orchestrator lists the files its workers changed; the git agent stages exactly those, never .work/ or someone else's edits, and runs a secret check before every commit.

      No shortcuts

      Force pushes, rebases, resets, amends, tags and --no-verify only when the Git line asks, and never to get another step through. A failing hook, a rejected push or a secret-check hit stops it, and the report says why and lists the commands; the orchestrator never retries it on its own.

      Isolation

      wf sessions

      The launcher runs claude --plugin-dir <install folder>/plugin --settings <install folder>/wf-settings.json --agent wf:orchestrator with a few environment variables: 10 minute Bash timeouts, workers cannot start agents of their own, the compaction trigger (8), and CLAUDE_CODE_THRIFTY_SONIC=0, which turns off a Claude Code reminder to change files with sed or scripts, so workers edit with Write and Edit, and CLAUDE_CODE_DISABLE_FAST_MODE=1, which turns off fast mode for every model in wf sessions. The plugin, the settings and the variables exist for that session only.

      Plain claude

      No wf agent, skill, hook, setting or variable. The one global file is ~/.claude/rules/wf-house-rules.md, on purpose. Install never writes settings.json, except the one-time v1 migration.

      Concise answers

      wf-settings.json sets "outputStyle": "Concise", Claude Code's built-in style, for the main thread; it wins over a project's own. Subagents never get an output style, so every worker's rules carry a short Reply style: lead with the result, no preamble or recap, short by default, but errors, failing checks, warnings and the result block always complete.

      House rulesCode in English (Hungarian only in i18n data), no comments in code except TODO, never commit, push or run any other git write unless asked (for wf: only wf:git, only when the approved summary says so, exactly the git work the summary's Git line names: any git or gh command is allowed for that work, such as deleting branches, a force push, a push or commit to main, rebase, reset, tags, amend and merge, and nothing the Git line does not name; unless the Git line says otherwise it commits on a feature branch and opens a pull request), never an em or en dash, and every behavior change updates, in the same task and unasked, all docs and guidelines that describe it (README, docs/, guides, changelogs, skills, agent prompts, rule files): a change is not done while any of them still describes the old behavior. Workers never delete with rm and a glob, a variable or a relative path.
